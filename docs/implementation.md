# Depter, Этап 1: долги, фото-основание, сторно, ссылка клиента

Основание: обновлённое ТЗ Depter, Этап 1 (25.09.2026) — цифровая тетрадь долгов
магазина стройматериалов, без остатков товара. Next.js App Router, TypeScript,
Supabase Auth и PostgreSQL; русский интерфейс, KGS, Asia/Bishkek.

## Завершённые этапы

### Foundation и справочники

- Таблицы плана плюс `audit_events`, `share_links`, read models и индексы.
- Денежные значения `numeric(16,2)`. Долг контрагента считается из проведённых
  операций (`sales`/`purchases`/`payments`), не хранится как редактируемое поле.
- Вход email/password для заранее созданных пилотных пользователей (вход по
  телефону+SMS/WhatsApp OTP+PIN из ТЗ — отдельная задача, нет провайдера OTP).
- Responsive shell, dashboard, CRUD клиентов/поставщиков с поиском, пагинацией
  и серверной валидацией. Товары/склад (`products`, `inventory_movements`,
  `product_balances`) — код и таблицы оставлены, но скрыты из навигации: это
  Этап 2 по ТЗ, не Этап 1.

### Долги: приход, продажа, оплата — с фото и сторно

- `commit_purchase`, `commit_sale`, `commit_payment` — сумма вручную, долг
  меняется сразу, без ожидания. RPC проверяют членство, идемпотентны, валидируют
  входные данные, работают в одной транзакции.
- Фото накладной/чека обязательно для прихода и продажи, необязательно для
  оплаты. Загружается в Supabase Storage (`receipts`), создаётся `documents`
  через RPC `create_document`, документ привязывается к операции (`document_id`).
- Сторно (`reverse_sale`/`reverse_purchase`/`reverse_payment`): запись не
  редактируется и не удаляется — помечается `reversed_at`/`reversal_comment`,
  снимается с баланса, но остаётся видимой в истории (зачёркнутой).

### Заявки клиента «Я оплатил» и ссылка без входа

- `share_links` + RPC `create_share_link`/`revoke_share_link` — токен 32 hex
  символа (v4 UUID без дефисов, ~122 бита случайности; на реальном проекте с
  pgcrypto можно перейти на `gen_random_bytes(16)` для честных 128 бит).
- Публичная страница `/c/<token>` (без авторизации, отдельный anon-клиент):
  долг, история операций, кнопка «Я оплатил» (сумма + фото чека + комментарий).
- Заявка создаёт `payments` со `status='pending'` — баланс не меняется, пока
  магазин не подтвердит (`confirm_payment_claim`, с возможностью поправить
  сумму) или не отклонит (`reject_payment_claim`, с комментарием). Экран
  «Заявки» (`/claims`) — список ожидающих с фото квитанции.

### Итог дня и акт сверки

- `/day` — живой пересчёт на выбранную дату: продано (в долг/наличные), кому
  продал, собрано (наличные/перевод), долг клиентов утром→вечером, поставщики,
  незакрытые заявки. Без снапшота/кнопки «Закрыть день» — см. ограничения ниже.
- `/[customers|suppliers]/[id]/statement` — акт сверки за период: сальдо на
  начало/конец, список операций, печать через `window.print()` и `@media print`
  (PDF-сервиса нет — печать браузера).
- «Напомнить» на карточке клиента — `wa.me`-ссылка с суммой долга и ссылкой на
  страницу клиента (без WhatsApp Business API).

### ADRE — фоновое распознавание фото (Gemini)

- `docs/pilot-plan.md` (старый 7-дневный план) описывает ADRE как часть
  товарно-складского учёта (создаёт товары, списывает склад) — это устарело
  вместе с остальной item-based моделью. Реализовано **по обновлённому ТЗ §6**:
  ADRE только оцифровывает уже проведённый документ, долг не трогает.
- `src/lib/adre/`: `types.ts` — `RecognitionProvider` и JSON-схемы
  `InvoiceResult`/`ReceiptResult` из ТЗ §6; `gemini.ts` — единственная сейчас
  реализация, структурированный вывод через `responseSchema` (Gemini
  гарантирует форму JSON); `recognize.ts` — оркестратор: скачивает фото из
  Storage, вызывает провайдера, сверяет `qty×price=sum` и сумму строк с
  итогом операции (допуск 1 сом, как в ТЗ), ставит `digitized` либо `review`.
  Второй провайдер (Claude) не подключён — интерфейс уже это позволяет без
  изменений в вызывающем коде.
- `GEMINI_API_KEY`/`GEMINI_MODEL` — переменные окружения процесса Next.js:
  локально в `.env.local` (не в git), на проде — Vercel → Project → Settings
  → Environment Variables, а не файл в репозитории. В Supabase этот ключ не
  хранится — вызов Gemini делает сам Next.js-сервер.
- Без очереди (Redis+BullMQ из ТЗ §9 не поднимали для пилота): триггер — `after()`
  из `next/server` в `commitOperation`, планирует распознавание после ответа
  пользователю, не блокируя запись долга. Работает только на Node.js-сервере
  (не static export) — сознательное упрощение для пилота.
- Экран `/documents`: список со статусами («Ожидает» / «Распознаём…» /
  «Оцифрована» / «Расхождение» / «Ошибка» с кнопкой «Повторить»);
  `/documents/[id]`: фото + строки накладной (редактируемые, `confidence<0.8`
  подсвечена жёлтым, несовпадение `qty×price` — красным), сравнение суммы
  строк с итогом по операции, для чека — карточка распознанных полей без
  редактирования. Бейдж количества `status='review'` в навигации.
- Не сделано в этом заходе: клиентские фото (заявка «Я оплатил» с публичной
  страницы) не запускают распознавание — продавец и так видит фото при
  подтверждении заявки; ретраев по расписанию нет, только ручная кнопка
  «Повторить»; оценка стоимости (`document_extractions.cost`) — приблизительная
  (по токенам ответа), не биллинговая.

### Синонимы контрагента и оплата по квитанции (закрыто следом за ADRE)

- `src/lib/match.ts`: `similarity()`/`bestMatches()` — коэффициент Дайса по
  биграммам, без `pg_trgm` (недоступно в PGlite) и без внешних библиотек.
- RPC `add_counterparty_alias` (миграция `20260925160000_counterparty_alias.sql`)
  — сохраняет распознанное имя в `aliases`, идемпотентно.
- `/documents/[id]`: для прихода/продажи сверяет распознанного контрагента с
  уже выбранным (по имени и алиасам); при низком совпадении — баннер и кнопка
  «запомнить как синоним». Долг это не меняет, только пометка на документе.
- `/money/new?type=payment`: блок «Есть фото или скриншот квитанции?» —
  распознаёт **синхронно** (это часть диалога с продавцом, не фон), предлагает
  клиента по имени отправителя (`bestMatches`) и подставляет сумму/номер
  перевода в форму до подтверждения оплаты — реализует сценарий В.2 из ТЗ §4.
  Ограничено входящими оплатами (клиент платит), как и в самом ТЗ.
  Компромисс: после подтверждения фоновое распознавание (`after()`) всё равно
  запускается ещё раз для этого же фото — двойной вызов Gemini, простое и
  надёжное решение ценой лишнего запроса; можно оптимизировать позже, переиспользовав
  результат синхронного вызова вместо повторного.

### Тип документа по ADRE

Схема ТЗ §6 для накладной включает `document_type` (`invoice_in`/`invoice_out`)
— это распознавание по содержимому фото, независимое от того, какую кнопку
(«Приход»/«Продажа») нажал продавец при загрузке (`documents.kind`). Раньше
это поле извлекалось, но нигде не показывалось. На `/documents/[id]` теперь
видно «ADRE увидел: накладная от поставщика / клиенту»; если это не совпадает
с `kind` документа — предупреждение («не похоже на …, проверьте фото»).
Классификация самого документа (`kind`) не меняется — это по-прежнему то, что
выбрал продавец нажатием кнопки; ADRE только сверяет и предупреждает.

### Нормализация извлечённых данных

Раньше вывод Gemini сохранялся как есть, без унификации — конкретный риск:
десятичная запятая ("240,00") не парсится в JS (`Number` → `NaN`), и сверка
`qty×price=sum` тогда молча считалась «сошедшейся», хотя не проверялась
вовсе. `src/lib/adre/normalize.ts` (`normalizeInvoiceResult`) приводит перед
любым использованием: разделитель дробной части к точке, единицу измерения —
к тому же набору, что и `products.unit` (шт/м/кг/упак/л, с картой синонимов:
"штук"→"шт", "кг."→"кг" и т.д.), название — обрезка пробелов. Применяется в
двух местах, где приходит сырой результат от провайдера: `recognizeDocument`
(фон) и `recognizeInvoicePhoto` (мгновенная проверка); `finalizeInvoiceRecognition`
нормализует ещё раз на всякий случай — результат мог побывать в браузере
(JSON в скрытом поле формы). Промпт Gemini (`gemini.ts`) также явно просит
формат с точкой и канонические единицы — нормализация страхует, если модель
всё равно отклонится.

### Мгновенная сверка суммы для прихода/продажи

- `recognizeInvoicePhoto` (`src/app/(workspace)/money/actions.ts`) — вызывается
  прямо с клиента (`operation-form.tsx`, `"use client"`) при выборе фото, без
  `<form>`-сабмита и без перехода/перезагрузки страницы; загружает фото и сразу
  распознаёт, возвращает результат в компонент.
- Пока идёт запрос — «Проверяем фото…»; после ответа — «По фото распознано: N
  сом» с пометкой «совпадает» / «отличается от введённой суммы» (допуск 1 сом)
  и кнопкой «Подставить», если поле суммы ещё пустое.
- В отличие от квитанции — здесь **нет** повторного вызова Gemini при
  подтверждении: результат проверки уходит в форму скрытым полем
  (`recognized_result`), и `finalizeInvoiceRecognition` (`src/lib/adre/recognize.ts`)
  просто записывает его (`start_recognition`→`save_recognition`) без похода к
  провайдеру ещё раз. Если проверка не удалась (нет ключа, сеть) — форма тихо
  откатывается к прежнему поведению: обычная загрузка фото при подтверждении и
  фоновое распознавание как раньше.

### Фирменный PDF (накладная и акт сверки)

- `@react-pdf/renderer` — чистый JS-рендер в Node, без headless-браузера
  (важно для Vercel serverless, где Playwright/Puppeteer требуют отдельной
  настройки бинарников).
- Шрифт **PT Sans** (`public/fonts/PTSans-Regular.ttf`, `-Bold.ttf`, ParaType,
  OFL-лицензия) — встроенные шрифты react-pdf кириллицу не поддерживают.
  Регистрируется по HTTP-URL исходного домена запроса (`src/lib/pdf/fonts.ts`),
  а не через `fs.readFileSync` — файлы в `public/` не гарантированно
  присутствуют в файловой системе serverless-функции на Vercel.
- `GET /documents/[id]/pdf` и `GET /[customers|suppliers]/[id]/statement/pdf`
  — отдают `application/pdf` с `Content-Disposition: attachment`. Данные для
  акта сверки вынесены в `src/lib/statement-data.ts`, общий для страницы и PDF.
- Предел WhatsApp: `wa.me` открывает чат только с текстом — автоматически
  прикрепить файл к сообщению без WhatsApp Business API невозможно ни у нас,
  ни у кого без него. Реалистичный сценарий — скачать PDF и прикрепить вручную.
- Не сделано: PDF накладной на публичной странице клиента (`/c/[token]`) —
  потребует отдельной публичной RPC по токену на конкретный документ,
  аналогично `get_statement_by_token`; клиент пока видит те же данные текстом
  на самой странице.

## Проверки

`npm test` использует PostgreSQL runtime PGlite и покрывает RLS, tenant
isolation, запрет прямой записи в регистры, атомарные ERP RPC, идемпотентность,
сторно, заявки на оплату (pending → confirmed/rejected), доступ по токену,
привязку фото к операции (в том числе межорганизационную защиту) и SQL-слой
ADRE (`start_recognition`/`save_recognition`/`fail_recognition`/
`confirm_document_lines`, RLS на `document_lines`). Сетевые вызовы Gemini
тестами не покрыты — `recognize.ts` изолирует вызов провайдера в одну функцию,
проверено вручную с реальным `GEMINI_API_KEY`. Блок Storage
в миграции (bucket + RLS-политики) — no-op под PGlite (в тестовой схеме нет
`storage`), поэтому применение этой части миграции нужно один раз проверить
руками на реальном Supabase-проекте перед пилотом. `npm run typecheck`,
`npm run build` и `npm run test:smoke` проверяют приложение локально. Это не
является проверкой облачного Supabase Auth или PostgREST.

Отдельный локальный `/preview` разрешён только при `ONGOY_PREVIEW=1` и
`NODE_ENV != production`, показывает пустой интерфейс и не открывает Auth API.

## Сознательно не сделано в этом заходе (нужна внешняя инфраструктура)

- Второй AI-провайдер (Claude) как резерв к Gemini — интерфейс готов, ключа нет.
- WhatsApp Business API (автонапоминания по расписанию) — сейчас только
  `wa.me`-ссылки, отправляемые продавцом вручную.
- Вход по телефону + SMS/WhatsApp OTP + PIN — сейчас email/password.
- Подписка/биллинг, роли сотрудников, несколько точек в одном аккаунте — Этап 2.
- Снимок «Закрыть день» (day_close): `/day` показывает текущее состояние на
  сейчас, а не сохранённый снапшот на момент закрытия; PDF «Итог дня» не
  генерируется.

## Ограничения пилота

Для нескольких организаций пока выбирается первая по времени членства;
переключателя нет. Создание ограничено тремя организациями на пользователя.
Все участники пилота имеют одинаковые возможности справочников. ERP RPC
сериализуют проведение по строке организации, что сознательно ограничивает
параллелизм для простоты и целостности пилотного журнала. Cloud Auth, Storage
и Vercel требуют отдельного подключения и не считаются проверенными локальной
сборкой.
