# Oŋoy: первый рабочий этап

Основание: pilot-plan.md, указание пользователя начать реализацию 25 сентября 2026.

Цель: foundation и справочники, которые можно подключить к отдельному Supabase без замены архитектуры.
Next.js App Router + TypeScript; Supabase Auth и PostgreSQL; русский интерфейс, KGS, Asia/Bishkek.
Один пользователь может состоять в нескольких организациях, пилот работает с первой доступной.
Все tenant-ссылки составные, RLS проверяет членство. Нет service-role в веб-приложении.

1. Создать 13 таблиц плана + audit_events, read models и индексы. Денежные значения numeric(16,2), количество numeric(16,3). Склад только из движений, долг только из проведённых операций. Клиент не может напрямую писать в регистры.
2. Вход email/password для заранее созданных пилотных пользователей. Проверка getUser, cookie refresh через proxy. Создание организации через атомарную RPC с auth.uid() и защитой повторной отправки.
3. Responsive shell, dashboard, CRUD клиентов/поставщиков/товаров с серверной проверкой данных, поиском и пагинацией. Документы и операции обозначить как следующие этапы, не имитировать OCR или продажи.
4. Проверка SQL на реальном PostgreSQL runtime PGlite: RLS между организациями, межорганизационные ссылки, запрет записи в регистры, формулы, идемпотентность организации. Проверка сборки и браузера.
5. Сохранить исходники с lockfile, миграцией и инструкцией запуска; cloud provisioning только после выбора отдельного Supabase. Не изменять базы других приложений.

Отдельный локальный /preview разрешён только при ONGOY_PREVIEW=1 и NODE_ENV != production. Показывает пустой интерфейс, не содержит данных и не даёт обходить auth API.

Следующие этапы: транзакционные команды покупки/продажи/оплаты с блокировками и идемпотентностью; storage; асинхронный ADRE; review; duplicate detection; реальные документы и тесты клиента. Они не входят в отметку готовности foundation.

Риски проверки: изменённый organization_id; товар чужой организации; пользователь без членства; дробные/отрицательные значения; повторное создание организации. Все покрываются тестами данных/валидации. Cloud Auth и Vercel требуют отдельного подключения и не считаются проверенными локальной сборкой.
