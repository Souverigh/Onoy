## Что это

**Depter** — веб-приложение для магазинов стройматериалов в Кыргызстане:
цифровая тетрадь долгов клиентов и поставщиков с фото-основанием каждой
записи. Кодовое имя репозитория/пакета — `ongoy` (внутреннее, в интерфейсе
не показывается). ТЗ (обновлённая версия, Этап 1) лежит вне репозитория —
`C:\Users\erzha\Documents\ONOY\Depter — ТЗ, Этап 1.docx`; если нужно свериться
заново, читать через docx-скилл (Read не читает бинарные .docx напрямую).

Стек: Next.js 16 (App Router, TypeScript), Supabase (Postgres + Auth + Storage),
Vercel-деплой. Никакого service-role в приложении — всё через RLS и
security-definer RPC. Перед работой с API Next.js — читать
`node_modules/next/dist/docs/` (см. AGENTS.md: версия отличается от обучающих
данных; например, лимит тела server action — 1 МБ по умолчанию).

Пользователь пишет по-русски; интерфейс приложения — на русском.

## Что сделано (в хронологии, все пункты — рабочие, покрыты тестами где есть логика)

1. **Foundation** (до первой сессии): справочники, RLS, мультитенантность,
   `commit_purchase/sale/payment` — сумма долга вводится вручную, долг
   меняется сразу, без ожидания.
2. **Долги Этапа 1**: фото обязательно для прихода/продажи, необязательно
   для оплаты; сторно (отмена записи с комментарием, не удаление); заявки
   клиента «Я оплатил» + публичная страница `/c/[token]` без входа; итог дня
   (`/day`, живой пересчёт); акт сверки с печатью и PDF; напоминание —
   `wa.me`-ссылка.
3. **ADRE** (`src/lib/adre/`): распознавание фото через Gemini, фон через
   `after()`, статусы документа (ожидает/распознаём/оцифрована/расхождение/
   ошибка), экран `/documents`. Ключ — только в Vercel Environment Variables,
   НЕ в Supabase (Edge Function делали и откатили по просьбе пользователя).
4. **Синонимы контрагента**: `src/lib/match.ts` (коэффициент Дайса, без
   pg_trgm) + баннер на `/documents/[id]`.
5. **Оплата по квитанции**: синхронное распознавание чека до подтверждения,
   подсказка клиента по имени отправителя.
6. **Мгновенная сверка суммы прихода/продажи**: при выборе фото —
   распознавание сразу на той же странице, сравнение с введённой суммой,
   кнопка «Подставить».
7. **Фирменный PDF**: `@react-pdf/renderer`, шрифт PT Sans в `public/fonts/`,
   регистрируется по HTTP.
8. **Нормализация извлечённых данных**: `src/lib/adre/normalize.ts`.
9. **Тип документа по ADRE** на `/documents/[id]` + предупреждение при
   несовпадении с выбором продавца.
10. **Парсинг суммы с пробелом-разделителем тысяч** (`decimalInput`).

    промпте (писать полное название) + страховка `expandAbbreviatedNames` в
    `normalize.ts` — строка без слова из 3+ букв получает основу названия из
    строки выше с тем же разделителем («Щит - 8»). Работает и на кеше (без
    повторной оплаты); уже сохранённые `document_lines` не переписываются.

30. **Перенос тетради** (`/import?kind=customers|suppliers`, кнопка «Из
    тетради» на справочнике; миграция 12). Начальный долг = обычная запись
    журнала с `is_opening=true`: клиенту — продажа, поставщику — приход,
    аванс (минус) — оплата; без фото. Баланс/акт/страница клиента/отмена
    работают как есть, подписи «Долг из тетради» / «Аванс из тетради»
    (`statementEntryLabel`), Итог дня и история по дням такие записи не
    считают (`.eq("is_opening", false)`; а `laterMovements` — считает, это
    баланс). `import_opening_balance`: контрагент по id, по имени без учёта
    регистра или новый; один действующий перенос на контрагента
    (`opening_exists`), исправление — отмена и новый перенос; идемпотентно по
    ключу строки. Экран: фото страниц (до 5) → Gemini `recognizeNotebook`
    (итоговый остаток по человеку, фото не сохраняются и не кешируются) →
    редактируемые строки с подбором из справочника (`bestMatches` ≥0.85 —
    автоматически, 0.45 — кнопки «Это X?») → «Сохранить долги» (каждая
    строка отдельно, повтор безопасен).

31. **«Закрыть день»** (миграция 13). Расчёт итогов вынесен в
    `src/lib/day-summary.ts` (`computeDaySummary`, `dayHistory`,
    `afterClosing`, `dayClosure`) — им пользуются `/day`, действие
    `closeDay` и `/day/pdf`. Закрытие считает итоги на сервере и сохраняет
    снимок (`DaySummary`, version 1) через `close_day`; повтор не
    перезаписывает. Закрытый день показывается по снимку (и в таблице «По
    дням» тоже), а записи этого дня, внесённые или отменённые после закрытия,
    — в блоке «После закрытия» (по `created_at`/`reversed_at` > `closed_at`).
    Добавлен блок «Кто оплатил». PDF «Итог дня» (`src/lib/pdf/day.tsx`): у
    закрытого — снимок + «после закрытия», у открытого — «цифры на сейчас».
    Push в 20:00 из ТЗ не сделан (нет push-инфраструктуры). PDF живым
    рендером не проверялся — шаблон как у акта сверки.

32. **PDF как документ** (без миграции): накладная, чек и страницы тетради
    принимаются фото или PDF (`DOCUMENT_ACCEPT`, `isPdf`, `MAX_UPLOAD_BYTES`
    в `src/lib/pages.ts`; сервер отклоняет другие типы). В форме
    прихода/продажи две кнопки: «Сфотографировать» (`capture`, камера) и
    «Выбрать фото или PDF» (без `capture` — иначе Android не даёт выбрать
    файл); у квитанций и на странице клиента `capture` убран (скриншот/PDF из
    банка). PDF не ужимается — общий размер > 3.8 МБ отсекается в браузере.
    Gemini получает PDF как `inline_data` `application/pdf`; при PDF
    добавляется `multiPagePrompt`. Просмотр `/documents/[id]`: PDF во
    `<iframe>` + «Открыть PDF отдельно» (мобильный Chrome PDF во фрейме не
    рисует). **Живым вызовом Gemini с PDF не проверено.**
    `DOCUMENT_ACCEPT` — явный список (application/pdf, image/jpeg/png/webp/
    heic/heif + расширения), **без `image/*`**: с ним Android открывал только
    камеру/галерею и PDF было не выбрать. Тип файла без MIME (HEIC) —
    `documentMimeType` по расширению, проверка — `isAcceptedDocument`.

33. **Отправка клиенту накладной в WhatsApp** (ТЗ §4 Б, миграция 14).
    Страница `/money/send/[saleId]`, на неё ведут: ссылка в сообщении после
    продажи (`/money?created=sale&sale=<id>`), «Отправить» в истории карточки
    клиента, «Отправить клиенту» на `/documents/[id]` продажи. Решения
    пользователя: **файл + ссылка**; **PDF только после сверки** (документ
    `digitized`, в т.ч. после «Подтвердить оцифровку»), до этого уходит текст
    с суммой и долгом. Текст — `src/lib/invoice-message.ts`. Кнопка
    (`src/components/send-invoice.tsx`): если браузер умеет
    `navigator.canShare({files})` — PDF (`/documents/[id]/pdf`) качается
    заранее и уходит через системное «Поделиться» файлом с текстом, рядом
    «Только текст со ссылкой» (wa.me); иначе — wa.me с текстом, в нём ссылка
    на публичный PDF `/c/[token]/invoice/[saleId]` (inline). Пока документ
    распознаётся — страница сама обновляется (до 1 мин). Ссылку клиента
    страница создаёт сама, если её никогда не было; если отозвана — не
    создаёт, сообщение без ссылок. На `/c/[token]` у сверенных продаж —
    «Накладная PDF». **На телефоне не проверено** (share с файлом в WhatsApp,
    подпись к файлу — Android WhatsApp может потерять текст; тогда есть
    кнопка «Только текст»). Не сделано: превью-картинка из ТЗ, запись факта
    отправки в историю, `show_lines_to_client`.

34. **Скидка в накладной** (миграция 15). Строка «Скидка -200» ломала
    `save_recognition` (check `price >= 0`) → документ «Ошибка». Теперь
    отрицательная цена разрешена; `lineShape` в `normalize.ts`: строка без
    qty/price, но с суммой → `1 × сумма`, отрицательное qty (возврат) → знак
    в цену. Работает и на кеше: после миграции «Повторить распознавание» не
    вызывает Gemini повторно. В правке строки на `/documents/[id]` цену можно
    ввести с минусом.

35. **Дата оплаты из чека** (миграция 16). `prepareReceiptPayment` берёт
    `datetime` чека → `receiptDateTime` (`src/lib/receipt-date.ts`: форматы
    «26.09.2026 14:35», «6.9.26», ISO, ISO с зоной → время Бишкека) →
    `?date=` → поле «Дата и время перевода (из чека)» (`datetime-local`) в
    форме оплаты; продавец может поправить. Поле есть и у оплаты без чека:
    пусто — «сейчас». Сервер: `bishkekDateTime` (+06:00) → `p_occurred_at`
    (передаётся только если задана). В промпте чека попросили формат
    ГГГГ-ММ-ДДTчч:мм; PROMPT_VERSION не менялся — старый кеш читается тем же
    разбором. Оплата прошлым днём попадает в Итог того дня; если день закрыт —
    в «После закрытия». Чек, приложенный уже в форме (без «распознать сразу»),
    дату не подставляет. Заявки клиента «Я оплатил» — по-прежнему дата заявки.
    Из накладной дата/номер всё ещё не используются.

36. **Напоминание «день не закрыт»** (без миграции). `unclosedDays` в
    `day-summary.ts`: прошлые дни за 7 дней (`UNCLOSED_LOOKBACK_DAYS`), где
    есть действующие записи (продажа/приход/подтверждённая оплата, не перенос)
    и нет `day_closures`. Дни без записей не считаются. Баннер
    `UnclosedDays` (жёлтый, как у заявок) — на главной и на `/day` (кроме
    открытого сейчас дня), ссылки на `/day?date=…`. Автозакрытия нет —
    решение пользователя: только напоминание. Push обсуждался — см.
    «Открытые вопросы».

37. **Лимит долга клиента** (ТЗ §4 Б, миграция 17). Поле «Лимит долга, сом
    (необязательно)» в карточке клиента (`directoryInput`: пусто → null).
    Форма продажи: `creditLimitExceeded` (`src/lib/credit-limit.ts`, в
    тийынах) по долгу клиента + введённой сумме; за наличные не считается.
    Превышение — красное «Долг станет X — больше лимита Y», продажу **не
    блокирует** (ТЗ: предупреждение). Ровно лимит — можно. Карточка клиента:
    «· лимит Y» и метка «больше лимита». В списке клиентов лимита нет.

38. **Обещанная дата и просрочка 30/60/90** (ТЗ §3, §9; миграция 18).
    Решение пользователя: просрочка — **от даты неоплаченной продажи** (FIFO:
    оплаты гасят самые старые продажи; продажи за наличные и отменённые не
    считаются). Считает вид `customer_debt_aging`. Карточка клиента: блок
    «Срок и давность долга» — обещанная дата (форма, `setPromisedDate`:
    сегодня…+год, пусто — убрать; `promisedDateInput` в `src/lib/promise.ts`),
    «Обещал до X — прошло N дн.» красным, раскладка по 4 корзинам.
    Напоминание в WhatsApp дописывает «Вы обещали оплатить до X» / «Срок
    оплаты — X». Список клиентов: фильтр «Все / Просрочено 30+ / 60+ / 90+»
    (`?overdue=`), метки «долг N дн.» (>30) и «нарушил срок». Главная:
    «Просрочено больше 30 дней: N клиентов, X сом →». Страница клиента
    `/c/…`: «Срок оплаты — до X». Обещание показывается, только пока есть
    долг. **Ограничение:** долг из тетради (`is_opening`) стареет с даты
    переноса, а не с настоящей даты долга. Сортировки по долгу нет (balance в
    виде — text). Автонапоминаний «за день до срока» нет (это WhatsApp API,
    Этап 2).

39. **Итоги недели и месяца с графиками** (ТЗ §3, без миграции). Страница
    `/reports` («Итоги» в меню и бургере, иконка `chart`). Неделя с
    понедельника, месяц календарный (`src/lib/periods.ts`: `period`,
    `change`, `niceMax`); листание назад `?offset=-N`, будущее не открывается.
    Сравнение — с тем же числом дней прошлого периода (1–27 сент против 1–27
    авг), процент со стрелкой и суммой. Плитки: продано (в долг / наличными /
    число продаж), собрано с клиентов, приход, оплачено поставщикам — те же
    правила, что Итог дня (без переносов и отменённых). Графики «Продано /
    Собрано по дням» — `src/components/day-columns.tsx`, HTML/CSS-столбцы (не
    SVG, чтобы подписи не мельчали на телефоне), один ряд — без легенды,
    подсказка по наведению/нажатию, будущие дни заштрихованы. Топ-5 должников
    (долг на сейчас) и таблица по дням со ссылками на `/day`. Данные —
    `src/lib/period-report.ts` (по 3 запроса на период + балансы/давность).
    Проверено скриншотом макета на 390 px, живьём — нет.

40. **«Оплатить часть» при приходе + правка суммы заявки** (без миграции).
    Форма прихода: поле «Сразу оплатили поставщику, сом (необязательно)»,
    не больше суммы прихода (`?error=part`). После `commit_purchase` —
    отдельный `commit_payment` outgoing со своим ключом
    (`part_payment_key`, второй `randomUUID()` на странице), без фото.
    Приход и оплата не атомарны: если оплата упала, приход остаётся, на
    `/money` красное «внесите оплату отдельно» (`&part=failed`), иначе
    «Оплата поставщику X записана» (`&part=<сумма>`). Только для прихода —
    у продажи есть «оплатил наличными» целиком. Заявки клиента: изменение
    суммы при подтверждении уже было (`confirm_payment_claim` принимает
    сумму); исправлено — поле принимает «5 000» с пробелом, неверная сумма
    даёт `?error=invalid` вместо падения страницы.

41. **Сверка трёх сумм накладной** (без миграции). `src/lib/adre/reconcile.ts`
    (`reconcileInvoice`, `TOLERANCE`=1 сом, общий для сервера и форм):
    строки (qty×price против суммы строки), наш итог по строкам против
    «Итого» на бумаге (`total_declared`, раньше извлекался, но не
    использовался) и против суммы в записи. «Оцифрована» — только если
    сошлось всё, что есть; итога на бумаге нет (null/0) — как раньше. Ловит
    пропущенную строку, когда продавец ввёл сумму по строкам, и ошибку в
    сложении на бумаге. Форма: «По строкам X · «Итого» на бумаге Y —
    совпадает/отличается» + пояснение при расхождении с бумагой; исправлен
    баг — сумма с пробелом («54 270») давала NaN и ложное «совпадает».
    `/documents/[id]`: «Строки · На бумаге · В записи» и пояснение. Уже
    оцифрованные документы статус не меняют.

42. **Экспорт в Excel** (ТЗ §9, без миграции). `/export` (вся база, лист на

43. **Скидка и возврат товара** (ТЗ §5 adjustment; миграция 19). Хранятся в

## Практика (полезно повторить)

- На архитектурные развороты — план, особенно если меняется схема БД или
  основной поток данных; на неоднозначные продуктовые решения (блокировать
  или предупреждать, окно поиска и т.п.) — спросить пользователя
  (AskUserQuestion), а не решать самому.
- Баг из скриншота — **сначала Vercel runtime logs**: оба бага этой сессии
  (`invalid_supplier`, 23505 по `file_hash`, дубль `sales_organization_id_document_id_key`)
  были видны только в логах, а скриншот показывал вторичный симптом.
  После `redirect()` все поля формы визуально сбрасываются.
- Перед использованием конкретной версии/параметров внешней модели —
  проверять через WebSearch/WebFetch (ai.google.dev), не по памяти.
- Heredoc с кириллицей и кавычками в Bash-инструменте на этой машине
  (Windows, Git Bash) иногда ломается («unexpected EOF») — надёжнее писать
  Python-скрипт правок во временный файл через Write и запускать его.
- Пользователь коммитит/пушит сам — не коммитить без просьбы, перед
  предположениями «надо запушить» проверить `git status`/`git log`.
- Каждая новая миграция: сказать, что её нужно запустить **до** пуша кода,
  если код выбирает новые колонки/таблицы (иначе страницы падают на проде).
- Требование пользователя: данные каждого магазина изолированы (RLS,
  `organization_id`, составные FK), существующие записи миграциями не
  переносить и не переписывать — только добавлять.
- Поля выбора файла: не использовать `accept="image/*"` вместе с PDF и
  `capture` на кнопке «выбрать файл» — на Android это открывает только
  камеру/галерею. Камера — отдельной кнопкой с `capture`.
